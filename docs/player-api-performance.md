# 선수 API의 최초 조회 성능

2026-10-03, 기존 서버와 DB를 읽기 전용으로 조사했다. 기존 캐시를 삭제하지 않고 별도 임시 디렉터리에서 `deploy/profile-api-performance.php`로 측정했다.

확인한 병목:

- 서버 RAM 약 950MiB, 조사 시 가용 약 482MiB.
- MariaDB 11.2.3의 `innodb_buffer_pool_size`가 16MiB(16777216바이트).
- `vmstat`의 I/O 대기 99~100%. 이 수치는 조사 당시 부하이며 상시 상태라고 단정하지 않는다.
- 여러 전체 리그 조회가 동시에 실행 중이었다. 일부는 200초 넘게 `Sending data` 상태였다.
- 경기 일지만 요청해도 리그 전체 집계로 ERA+ 등의 불필요한 주요 기록을 계산했다.
- 타자는 경기 일지와 연속 경기 기록에서 같은 올해 타석을 두 번 조회했다.

적용한 코드 변경:

1. 경기 일지의 `gamesOnly` 경로는 리그 평균, 최근 성적, 은퇴 통산 집계를 생략한다. 경기 상세 값은 유지한다.
2. 올해 정규시즌 일지에서 읽은 타석을 연속 기록에 재사용한다. 필요한 과거 시즌 조회와 오늘 이후 경기 제외는 유지한다.
3. 시즌 목록은 기존 `idx_search_league_player_game` 인덱스만 읽어 경기 단위로 먼저 중복을 제거한 뒤 일정에 연결한다.
4. 연도별 투수 기록의 반복 배열 복사를 제거했다. 타자의 비정규시즌에서 사용하지 않는 전체 투수 리그 집계도 생략한다.

김현수(76290)의 136경기 조회는 최종 수정 전 67.36초, 수정 후 49.00초였다. 원격 DB의 동시 부하와 버퍼 상태가 달라 정밀한 A/B 성능 보장으로 해석하지 않는다. 리그 집계를 제외하고도 단일 타석 조회가 15~20초 걸린다는 점은 서버 I/O 병목이 남아 있다는 근거다. 전체 리그를 다시 집계하는 기준 측정은 수 분 동안 완료되지 않아 이번 작업에서 시작한 측정 프로세스만 중단했다.

다음 조치안:

- InnoDB 버퍼는 사용자 승인 후 256MiB(268435456바이트)로 조정했다. 가용 메모리·스왑 입출력을 계속 관찰하고 문제가 생기면 기존 16MiB로 복구한다. 웹/PHP도 같은 RAM을 사용하므로 DB 전용 서버의 메모리 비율을 그대로 적용하지 않는다.
- 리그 ERA/FIP 기준값과 선수별 시즌 합계를 크롤러 갱신 뒤 미리 계산해 영속적인 요약 데이터로 저장하면, 파일 캐시가 없어도 원본 전체를 집계할 필요가 없어진다. 이번 작업에서 크롤러나 이런 요약 테이블은 변경하지 않았다.
- 과거 완료 시즌과 현재 시즌의 집계 갱신을 분리하면 올해 크롤러 실행 때문에 과거 전 시즌을 다시 계산하는 일을 줄일 수 있다.

2026-10-03 KST, 사용자가 제공한 로컬 자격 증명 파일로 관리자 접속 후 `SET GLOBAL innodb_buffer_pool_size=268435456`을 실행했다. 비동기 확장 완료 상태와 실제 268435456바이트를 확인했다. `/opt/bitnami/mariadb/conf/bitnami/memory.conf`의 같은 항목도 16M에서 256M으로 변경했다. 기존 파일은 서버에 `memory.conf.before-buffer256-20261002T161534Z`로 백업했다(파일명은 서버 시계 기준). 비밀번호를 출력하거나 저장소에 복사하지 않았고, 비밀번호 초기화와 서비스 재시작도 수행하지 않았다.

변경 후 김현수(76290), 2026년 정규시즌 136경기, 별도 빈 PHP 캐시에서 첫 측정 18.55초, DB 버퍼가 따뜻해진 두 번째 측정 0.139초였다. 두 번째 측정도 PHP 캐시는 별도로 격리했다. 로컬 실제 `part=games` HTTP 응답은 200, 유효한 JSON, 0.525초였다(이 HTTP 측정은 캐시 상태를 통제하지 않았다). 최초 디스크 읽기와 동시 부하가 있는 상황의 모든 요청이 0.139초라고 보장하지 않는다.

확장 직후 가용 메모리 약 416MiB, 집계 측정 중 약 248~297MiB였다. 초기 3초 관찰에서 스왑 입출력은 0이었으나 이후 전체 리그 집계 도중 한 샘플에서 약 4MiB/s 스왑 쓰기와 작은 스왑 읽기가 관찰됐다. 재관찰 5초 동안 스왑 쓰기는 0, 읽기는 약 60~128KiB/s였다. 기존 스왑 사용량은 남아 있으며 전체 리그 집계의 I/O 대기도 남아 있다.

캐시 없는 연도별 기록도 선수 한 명으로 측정했다. 리그 타석 합계 쿼리가 140초 이상 `Sending data` 상태였고 전체 측정은 수 분 동안 완료되지 않았다. 운영 부하를 줄이기 위해 이번 작업의 해당 PHP 측정 프로세스만 종료했다. 이 경로의 완료 시간은 확보하지 못했으며, 버퍼 확대만으로 최초 연도별 기록 집계가 해결됐다고 주장하지 않는다.

코드 변경은 작업 디렉터리에 적용했으며 운영 PHP 배포는 하지 않았다. 경기 전용 경로, 연속 기록의 타석 재사용, 시즌 목록, 연도별 지표, 희생타, OPS+ 회귀 검증을 통과했다.
